\begin{abstract}
Study assistants based on local language models keep students' notes and questions on hardware
controlled by the institution, but they are usually designed for one student at a time: generating one
grounded answer can occupy the machine long enough for a class to form a queue, and the system does
not learn from the class as a whole. We demonstrate \sys{}, an open-source self-learning platform in
which all models run locally. A student uploads course notes and receives grounded chat with page
citations, practice questions, key points and summaries, each checked by a second model before use.
Since each document is stored once using its content hash, students who share lecture notes also share
one index and, during revision, often ask similar questions. \sys{} uses this sharing through four
mechanisms: hybrid dense and BM25 retrieval combined inside the vector database; a verified answer
cache that reuses a judge-approved answer only when a cross-encoder confirms that two students asked
the same question; a lease-based job queue feeding a worker pool and continuously batched model
servers; and confusion mining, which groups student questions by pages of the shared notes under a
$k$-anonymity floor. In an end-to-end run, reuse answered a repeated question about two orders of
magnitude faster than generating it again on the same machine, and a worker killed during an answer
had its job recovered by another worker.
\end{abstract}

\section{Introduction}

Large language models can explain, quiz and summarise course material on demand, and retrieval-augmented
generation (RAG) \cite{lewis2020rag} lets them answer from a student's own notes rather than from learned
knowledge alone, reducing unsupported answers. Running the models locally keeps the notes and questions
private, which matters to institutions that cannot send student data to third parties. The trade-off is
speed and scale: on a CPU, a 3B-parameter model generates one grounded answer much more slowly than a
class can wait, and one model instance handles one request at a time.

\sys{} started as a single-student assistant: a student uploads a PDF, Word, PowerPoint or \LaTeX{} file
and can ask questions or generate practice material from it, with a second model checking every output
first. One implementation detail makes larger-scale use possible. Documents are identified by the
SHA-256 hash of their bytes, so when thirty students upload the same lecture notes the file is stored,
cleaned, chunked and embedded \emph{once}, and all thirty use the same document. Revising for the same
exam, they also tend to ask similar questions in different wording.

This paper presents the working system and four mechanisms that turn one shared document into shared
capacity: \textbf{hybrid retrieval inside the vector database} (Section~\ref{sec:retrieval}); a
\textbf{verified answer cache} (Section~\ref{sec:cache}), where an accepted answer is reused only after a
cross-encoder confirms that the two questions match; a \textbf{lease queue and worker pool}
(Section~\ref{sec:serving}), letting many workers serve the class without losing a question when one
crashes; and \textbf{confusion mining} (Section~\ref{sec:mining}), a per-page map of where the shared notes
cause difficulty. All models run locally: Qwen2.5-3B-Instruct generates answers, Llama-3.2-3B-Instruct grades
them, and MiniLM models embed and rerank passages. The generator and judge use different model families on
purpose: a judge sharing the generator's weights may rate its own style highly, costing the quality gate its
usefulness. The code and the evaluation harness are
available.\footnote{\url{https://github.com/LearnMateAI/project}. Add the demonstration video link
here once the screencast is recorded; most demo tracks ask for one.}

\section{Related Work}

Hybrid lexical-dense retrieval and fusion methods are well studied \cite{cormack2009rrf}. \sys{} contributes an
engineering result rather than a new model: BM25 can run inside the vector database next to the dense index and
use the same tenant filter.
Semantic caches answer a new prompt with an earlier similar response \cite{bang2023gptcache}, where the main
challenge is a safe similarity threshold; vCache \cite{schroeder2025vcache} learns one per entry with an
error guarantee, whereas our approach suits a judged pipeline: a cross-encoder decides the match, and only
answers accepted by an LLM judge \cite{zheng2023judge} are stored, so a reused answer has passed two checks.
Continuous batching \cite{yu2022orca} is common in GPU serving; we contribute the queue design that lets a
local deployment use it without losing work when a worker fails. Confusion has been detected from course-forum
posts \cite{yang2015confusion}; \sys{} mines the questions students ask the assistant instead, mapped to pages
of the shared notes under $k$-anonymity \cite{sweeney2002kanon}.

\section{System Architecture and Technical Design}

\subsection{Platform, request path and data model}

The backend is a FastAPI web layer over an engine library (Fig.~\ref{fig:arch}). The engine does not
depend on HTTP or user management, while the web layer handles accounts (local bcrypt tokens or federated
Keycloak), access control and requests; that separation lets one service function handle both a web request
and a queued job. Upload, generation and chat all return \texttt{202 Accepted} with a job id that the browser
polls for progress and the result.

Ingestion validates the upload, stores its bytes in GridFS, cleans the text, divides it into chunks of at
most 900 characters that do not cross page boundaries, and embeds them. Chunk vectors go to Qdrant; data
that cannot be recreated goes to MongoDB, so losing Qdrant requires a re-index while losing MongoDB loses
the corpus. Since a document is keyed by its content hash, ownership cannot be a field on it: it lives in a
separate collection, one row per person per document, which every access check uses, and the bytes are
deleted only after the last owner deletes.

A chat turn is a compiled state machine over the nodes in Fig.~\ref{fig:arch}, with one conditional edge for
a retry. The mode is selected from the retrieval score rather than from another model. In \emph{pdf} mode the
best reranked chunk passes the threshold, so the answer is generated only from those chunks, includes page
citations, and is judged strictly against them. In \emph{general} mode nothing relevant is found, so the
contexts are removed to stop a weak passage grounding the answer, and the interface says so. Generated
resources pass two checks, cheapest first: structural validators in plain Python, then the judge, whose
critique feeds one regeneration. The gates fail closed, because unreviewed content should never pass
silently.

\subsection{Hybrid retrieval inside the vector database}
\label{sec:retrieval}

The original retriever returned the uncombined union of the top dense results and the top results from an
in-process BM25 index that was rebuilt in every server process, rescored every chunk for each query, and
did not stem, so \emph{duty} and \emph{duties} were different terms.

Both methods now run inside Qdrant. Okapi BM25 \cite{robertson2009bm25} has a document part---the
saturated, length-normalised term frequency
$tf(k_1{+}1)/(tf+k_1(1-b+b|d|/\overline{|d|}))$---and a query part based on inverse document frequency.
The document part is calculated during ingestion and stored as a sparse vector of stemmed,
stopword-filtered terms; the query part is calculated by the server from the collection's own
statistics, so no application process stores corpus statistics. Each request performs two prefetches,
dense and sparse, both filtered to the student's document, which is the collection's tenant key, fused
by reciprocal rank \cite{cormack2009rrf} with $k{=}60$; a cross-encoder then reranks the shortlist to the
three chunks sent to the prompt. An existing deployment migrates by copying dense vectors into the new
schema, and a configuration error falls back to the old union instead of failing a question.

\subsection{Verified answer cache}
\label{sec:cache}

Questions about one passage often share many content words. Two that differ only in \emph{advantages}
versus \emph{disadvantages}, or in a rule versus its exception, can therefore produce almost identical
embeddings, while real paraphrases can sit near $0.8$ cosine, so no single embedding threshold separates
these cases reliably. \sys{} therefore separates shortlisting from the final decision, as retrieval
separates search from reranking. A lookup embeds the standalone question and selects the three nearest
cached questions for the same document, generator, prompt version, embedding model and index version;
candidates above a cosine threshold are checked by a cross-encoder trained on duplicate question pairs,
and a hit requires its probability to exceed a second threshold.

Only answers accepted by the judge in pdf mode, and not created by rewriting a follow-up, are stored, because a
follow-up depends on a previous conversation the next student does not have. Entries expire and are invalidated
when the document is re-ingested or deleted. No user or session identifier is stored---the cache holds an answer
about a document, not who asked---and a hit returns the stored answer with its citations, marked as reused.

\subsection{Lease queue and worker pool}
\label{sec:serving}

The original design used one worker thread and an in-memory queue. One worker was \emph{correct}, not simply
inefficient: the in-process model has one mutable context, so two threads generating at once could corrupt
both replies. But it serialised the class, and a restart failed all waiting jobs.

The job records now act as the queue. A worker claims the oldest due job using one atomic
find-and-update operation and assigns a lease from the \emph{database's} clock, which makes lease
expiry consistent for workers on different machines. The worker renews the lease periodically and
writes the result only while it still owns the lease. A reaper returns expired jobs to the queue up to
a retry limit, so another worker finishes a job after a crash and a poisoned job cannot stop every
worker in turn, while a unique index makes persistence of a retried turn idempotent. The models run in
\texttt{llama-server} instances with parallel slots, which interleave tokens from concurrent requests
in shared forward passes---continuous batching \cite{yu2022orca}. If the models still run in-process,
the code forces the worker count to one, preserving the correctness rule even after a configuration
mistake.

\subsection{Confusion mining}
\label{sec:mining}

Since the document is shared, every student question about it is evidence about the \emph{document}. Two
MongoDB aggregation pipelines count inside the database: a window pass pairs each answer with the
preceding question, and a faceted pass calculates, per page, the number of questions, distinct students,
general-knowledge fallbacks and low-scored answers. A question is assigned to the page of its best
citation, or, if the document could not answer it, to the page retrieval came closest to, because that
page indicates where coverage was missing. Questions are clustered using HDBSCAN
\cite{campello2013hdbscan}, which finds the number of topics automatically and treats one-off questions
as noise, and each topic is labelled using class-based TF-IDF as in BERTopic
\cite{grootendorst2022bertopic}. A page's confusion score combines its share of class questions with
four signals that the answers did not succeed---general-knowledge fallback, a low score, a score still
low after retry, and the same student returning to the same topic within one week:
\begin{equation}
\mathrm{conf}(p) = \mathrm{vol}(p)\cdot\frac{1+\sum_i w_i x_i(p)}{1+\sum_i w_i},
\label{eq:conf}
\end{equation}
where $\mathrm{vol}(p)$ is the page's question count divided by the maximum across shown pages and $x_i(p)$
are the four signal rates. The components are returned with the score, because \emph{why} a page is flagged
matters more than the count. Pages and topics with fewer than $k{=}3$ contributing students are hidden, and
only topic keywords are shown, never question text.

\section{Demonstration Setup and Practical Scenarios}

% The end-to-end verification run used to be a table here. With Tables I and II now carrying measured
% benchmark results, its checklist is reported as prose in Section V-A instead, which the 4-page limit
% needs. The full run is recorded in IMPROVEMENTS.md in the repository.

The demonstration runs on one machine and needs no network after installation: MongoDB and Qdrant in
containers, the backend, a React frontend behind nginx, and two \texttt{llama-server} processes for the
generator and judge. The model weights total about 4\,GB, so a laptop is sufficient, and a health endpoint
reports both databases, both models and the queue depth. The material is one chapter of an open business-law
textbook \cite{valbrune2019bizlaw} and a pre-seeded simulated fortnight of questions from forty students.

\textbf{A grounded answer and a graded quiz.} Student~A uploads the chapter and asks what makes a contract
enforceable. The answer is streamed with a grounded label and citation chips that open the cited page in
the reader next to the chat, alongside the judge's score and the rejected first attempt with its critique.
Student~A then generates twenty multiple-choice questions for the chapter, distributed across page groups,
then pooled and de-duplicated.

\textbf{The same question from another student.} Student~B uploads the same file, which the hash
identifies, so it is not processed again. Student~B asks the same question in different wording and the
answer appears immediately with a reused badge, the similarity and verifier scores shown on hover. If
the student instead asks about the \emph{exception} to the rule---a near miss that looks almost
identical to an embedding model---the cached answer is not used.

\textbf{The lecturer's view.} The class-insights tab displays the heatmap after the simulated fortnight.
Darker pages drew more questions with poor outcomes, hatched pages were below the $k$-anonymity floor, and
topics carry badges such as ``40\% not answered from the notes''. Clicking a page opens it in the reader, so
the view ends at the paragraph that needs improvement.

\textbf{Many students, and a worker that dies.} Two worker processes consume jobs while the API only adds
them, so two students are answered at once. One worker is then killed during an answer: its lease
expires, the reaper returns the job to the queue, and the other completes the turn on the second attempt,
persisted only once.

\section{Evaluation and Performance Metrics}

\subsection{Harness, corpus and end-to-end verification}

Every number reported here is generated by a script in the repository's evaluation package rather than entered
manually. Each writes a JSON result recording the commit, machine and settings, and a value not yet produced is
shown as \textbf{??}. The harness uses its own database and vector container, so benchmarks cannot reach real
user data.

The corpus contains \val{CorpusDocs} chapters (\val{CorpusPages} pages, \val{CorpusChunks} chunks) from an
open law textbook \cite{valbrune2019bizlaw}, each ingested as one shared document. Following InPars
\cite{bonifacio2022inpars}, the local generator creates, for each of \val{WorkloadFamilies} sampled chunks,
one question answered by the chunk, two paraphrases, and a near miss needing a different
answer---\val{WorkloadQuestions} questions with a known source chunk. A simulated class of
\val{WorkloadStudents} students then
asks \val{WorkloadAsks} questions over two weeks, drawn by a Zipf distribution, with one chapter held out for
tuning thresholds.

A separate end-to-end run on a CPU-only laptop, against temporary stores, checks correctness rather than
speed: a 29-step smoke test passes 29/29 both with default settings and with all four features enabled, an
exact repeat is served from the cache about $100\times$ faster than a full turn on that machine, a near miss
is correctly not reused, a worker killed mid-answer has its job requeued on lease lapse and finished by its
peer, and two concurrent requests through one model server raise aggregate throughput by 30\%. Speeds are
ratios only, since a wall-clock time would describe the deployment's CPU or GPU, not \sys{}.

\subsection{Component benchmarks}

Retrieval is evaluated over \val{IRQueries} seed questions and paraphrases by Recall@3 and graded nDCG@10,
before and after reranking (Table~\ref{tab:ir}). The result is worth stating plainly. Fusion helps the
\emph{first stage}: both fused strategies and server-side BM25 beat the legacy union on every first-stage
column of Table~\ref{tab:ir}. After the cross-encoder, though, the strategies converge: RRF and the legacy
union both reach nDCG@10 \val{IRRrfNdcg} at Recall@3 \val{IRRrfRThree}\%, a difference that is not
significant ($p=\val{IRRrfPValue}$). On a single 341-chunk document the reranker recovers most of what the

questions sharing vocabulary with their source chunk. At this scale the benefit of moving BM25 into the
database is therefore architectural rather than a ranking gain---no process holds a lexical index, IDF is
shared, and one tenant filter covers both halves---and the fused first stage is what a weaker or absent
reranker would rely on. Retrieval score also decides each turn's mode, and it agrees with the ground truth
for \val{ModeAccuracy}\% of questions.

\subsection{Limitations}

The questions are LLM-generated and the class simulated; generated questions share vocabulary with their
source chunks, favouring lexical retrieval, so paraphrases are reported separately, and the simulation has
no judge scores, so two of the four confusion signals are absent from the mining evaluation. The corpus is
one English law textbook, the verifier was trained on general web questions, and no real students took part.

\section{Conclusion and Future Work}

\sys{} shows that a self-learning platform can run fully on local hardware while serving a class, by
treating a shared document as shared capacity: shared retrieval, shared verified answers, shared serving and
shared information about where the notes cause difficulty. The four mechanisms are independent, each enabled
through configuration, and each falls back to the previous behaviour rather than to an error, so a retrieval or
cache fault cannot lose a student's answer.

Three directions follow. The first is classroom deployment, which would calibrate the $k$-anonymity floor
against real class sizes and let students decide how reused answers are presented. The second is adaptive
thresholds: a per-entry error guarantee similar to vCache \cite{schroeder2025vcache} could allow more reuse
while reducing incorrect reuse. The third is closing the loop, since the page that causes the class most
difficulty is a natural target for extra practice generation.
